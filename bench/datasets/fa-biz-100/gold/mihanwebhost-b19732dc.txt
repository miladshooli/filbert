نیم سرور دامنه چیست و چگونه باید آن را تغییر داد؟

نیم سرور دامنه یا Name Server بخشی از زیرساخت DNS است که مشخص می‌کند اطلاعات مربوط به یک دامنه از کدام سرورهای DNS دریافت شود. به زبان ساده، وقتی کاربر نامی مانند example.com را وارد مرورگر می‌کند، DNS باید مشخص نماید این دامنه به چه سرویس یا آدرس شبکه‌ای مرتبط است. Name Server در این زنجیره وظیفه پاسخ‌گویی از روی داده‌های DNS را بر عهده دارد.

نیم سرور دامنه چیست و چه وظیفه‌ای دارد؟

Name Server سروری است که برای یک زون DNS، داده‌های لازم جهت پاسخ‌گویی را نگهداری یا پاسخ معتبر (authoritative) ارائه می‌کند. رکوردهایی مانند A، AAAA، MX، CNAME و TXT در Zone قرار می‌گیرند و مسیر وب‌سایت، ایمیل و سرویس‌های دیگر را مشخص می‌کنند. رکورد، اطلاعات مشخص را نگه می‌دارد و Name Server پاسخ به درخواست را ارائه می‌کند.

تصویر(1)

رابطه نیم سرور دامنه و هاست

دامنه، آدرس قابل‌خواندن برای انسان است و هاست یا سرور، محل اجرای وب‌سایت و سرویس‌ها می باشد. Name Server مسیر پیدا کردن اطلاعات DNS دامنه را مشخص می‌کند. بنابراین تغییر هاست لزوماً به معنای تغییر نیم سرور دامنه نیست. اگر DNS نزد همان ارائه‌دهنده باقی بماند، معمولاً فقط رکوردهای A یا AAAA تغییر می‌کنند؛ اما با انتقال مدیریت DNS به سرویس‌دهنده دیگر، معمولاً Name Server های ثبت‌شده در رجیسترار نیز باید تغییر نمایند.

فرایند پیدا شدن IP دامنه؛ از Resolver تا Authoritative

وقتی کاربر دامنه‌ای را درخواست می‌کند، دستگاه Query را به Recursive DNS Resolver می‌فرستد. اگر پاسخ در کش نباشد، Resolver به Root Server، سپس TLD Server مانند com. و در نهایت Authoritative Name Server دامنه مراجعه می‌کند. Authoritative Server پاسخ Zone را ارائه می‌دهد و Resolver آن را برای مدتی کش می‌نماید.

Resolver و Authoritative Nameserver چه تفاوتی دارند؟

Resolver برای کاربر جست‌وجوی DNS را انجام می‌دهد؛ Authoritative Nameserver مرجع اصلی داده‌های دامنه است. برای نمونه، DNS ارائه‌شده از سوی ISP یا سرویس‌های عمومی معمولاً نقش Resolver دارد اما Name Server هایی که در پنل رجیسترار برای یک دامنه ثبت می‌شوند، معمولاً به زیرساخت Authoritative DNS اشاره دارند. تغییر Resolver دستگاه کاربر، تنظیمات DNS دامنه را جابجا نمی‌کند.

تصویر(2)

تفاوت نیم سرور دامنه با DNS، هاست و DNS Record

DNS نام سامانه‌ای است که نام‌های دامنه را به اطلاعات شبکه مرتبط می‌کند. نیم سرور دامنه یکی از اجزای این سامانه می باشد و DNS Record داده مشخصی مانند IP، مقصد ایمیل یا نام مستعار را ارائه می‌کند. هاست نیز زیرساختی است که وب‌سایت یا برنامه روی آن اجرا می‌شود. بنابراین دامنه «نام»، DNS «سامانه»، Name Server «مرجع پاسخ‌گویی به رکوردها» و هاست «محل ارائه سرویس» است.

انواع نیم سرور دامنه در معماری DNS

از دید معماری DNS، چهار نقش اصلی وجود دارد:

Recursive Resolver: درخواست را از طرف کاربر دنبال نموده و پاسخ را کش می‌کند.

Root Name Server: ریزالور را به TLD مناسب هدایت می‌نماید.

TLD Name Server: اطلاعات مرتبط با پسوندی مانند com. یا org. را ارائه کرده و Resolver را به Authoritative Server دامنه هدایت می‌کند.

Authoritative Name Server: پاسخ معتبر Zone دامنه را ارائه می‌دهد.

در یک Zone ممکن است معماری Primary و سرور DNS ثانویه (Secondary DNS server) وجود داشته باشد؛ Secondary کپی داده authoritative را نگه می‌دارد و برای افزونگی و پایداری سرویس به کار می‌رود.

چرا باید نیم سرور دامنه را تغییر داد؟

تغییر Name Server زمانی انجام می‌شود که مدیریت DNS از یک ارائه‌دهنده به دیگری منتقل گردد؛ برای مثال هنگام مهاجرت به سرویس DNS مدیریت‌شده، انتقال زیرساخت یا افزودن قابلیت‌های امنیتی و مدیریتی جدید انجام می شود. اگر تنها IP وب‌سرور تغییر کرده باشد و DNS همچنان در سرویس قبلی مدیریت شود، معمولاً تغییر NS ضرورتی ندارد.

یک سناریوی رایج، انتقال DNS از رجیسترار به ارائه‌دهنده تخصصی DNS یا تغییر هاستینگ همراه با انتقال کامل مدیریت DNS است. در پروژه‌های سازمانی نیز تفکیک مدیریت دامنه از زیرساخت می‌تواند باعث جابجایی نیم سرور دامنه شود.

پیامدهای تنظیم نادرست نیم سرور دامنه

اگر نیم سرور دامنه اشتباه یا ناقص ثبت شود، Resolver نمی‌تواند پاسخ معتبر را برای دامنه پیدا کند. نتیجه ممکن است قطع سایت، اختلال ایمیل یا نمایش نتایج متفاوت در نقاط مختلف اینترنت باشد. بنابراین پیش از تغییر NS باید Zone مقصد آماده و رکوردهای ضروری بازسازی شده باشند.

تصویر(3)

راهنمای گام‌به‌گام تغییر نیم سرور دامنه

جهت تغییر نیم سرور دامنه لازم است تا مراحل زیر را طی نمایید:

۱. Name Server های مقصد را از ارائه‌دهنده DNS یا پشتیبانی هاست و سرور خود دریافت نموده و نام آن‌ها را دقیقاً کپی کنید.

۲. در سرویس DNS جدید، رکوردهای مهم مانند A/AAAA، CNAME، MX و TXT را پیش از تغییر NS ایجاد کنید. در هاست های اشتراکی این رکوردها به صورت پیشفرض وجود دارند.

۳. وارد پنل شرکت ثبت کننده دامنه شوید و بخش "مدیریت دامنه" را باز نمایید.

۴. NS های قدیمی را با Name Server های جدید جایگزین کرده و تغییرات را ذخیره کنید.

۵. پس از اعمال تغییر و گذشت حدود یک ساعت، توسط ابزارهایی مانند intodns.com یا ns-lookup.io، وضعیت NS و رکوردهای اصلی را بررسی نمایید.

DNS Propagation چیست و TTL چه نقشی دارد؟

اصطلاح DNS Propagation بیشتر به مدت زمان لازم برای منقضی شدن کش‌های قدیمی و دریافت پاسخ جدید اشاره دارد. TTL مشخص می‌کند پاسخ یک رکورد چه مدت می‌تواند در Resolver ها کش شود؛ TTL کوتاه‌تر معمولاً تغییرات را سریع‌تر قابل مشاهده می‌نماید، درحالی‌که TTL بلندتر کش طولانی‌تر ایجاد می‌کند. هیچ زمان ثابتی برای پایان Propagation وجود ندارد و نتیجه به TTL، کش‌های محلی و نوع تغییر وابسته است.

نیم سرور اختصاصی چیست و چگونه ساخته می‌شود؟

نیم سرور اختصاصی زمانی ساخته می‌شود که مجموعه‌ای مانند ns1.example.com و ns2.example.com به‌عنوان نیم سرور دامنه معرفی شوند. در این حالت باید روی زیرساخت DNS، سرویس authoritative فعال گردد؛ سپس برای نام‌های NS آدرس IP تعریف و در رجیسترار نیز چایلدهاست (Child Host) ثبت شود. روش دقیق به رجیسترار و نرم‌افزار DNS بستگی دارد.

Glue Record چیست و چرا در Name Server اختصاصی مهم است؟

Glue Record اطلاعاتی است که در Zone والد برای IP یک Name Server «داخل همان دامنه» قرار می‌گیرد. برای نمونه، اگر example.com از ns1.example.com استفاده کند، جهت پیدا کردن IP خود ns1.example.com یک وابستگی حلقوی ایجاد می‌شود؛ Glue این حلقه را می‌شکند تا Resolver از ابتدا بتواند به سرور authoritative برسد.

رفع اشکالات رایج بعد از تغییر Name Server

با تغییر NS، عیب‌یابی بهتر است از خود Delegation آغاز شود و سپس به رکوردهای Zone برسد. ابزارهای WHOIS و DNS Lookup می‌توانند مشخص کنند Name Server های ثبت‌شده چیست و پاسخ authoritative از کدام سرورها دریافت می‌شود.

باز نشدن سایت و خطای DNS_PROBE_FINISHED_NXDOMAIN: این خطا معمولاً زمانی دیده می‌شود که دامنه از دید Resolver وجود ندارد یا Delegation و Zone درست پاسخ نمی‌دهند. ابتدا لازم است DNS های دامنه و سپس رکورد A یا AAAA بررسی گردند؛ در صورت محدود بودن خطا به برخی شبکه‌ها، کش نیز می تواند دخیل باشد.

از کار افتادن ایمیل و رکوردهای MX و SPF: تغییر NS می‌تواند ایمیل را نیز مختل کند زیرا MX و رکوردهای TXT مربوط به SPF و سایر تنظیمات احراز هویت ایمیل باید در Zone جدید وجود داشته باشند. انتقال DNS بدون بازسازی این رکوردها ممکن است وب‌سایت را سالم نگه دارد اما ایمیل را متوقف کند.

تصویر(4)

نمایش سایت قبلی یا تفاوت پاسخ در اینترنت‌های مختلف: اگر کاربران مختلف پاسخ‌های متفاوتی دریافت کنند، باید کش، TTL و وضعیت NS های جدید و قدیمی بررسی شود. وجود TTL طولانی می‌تواند باعث شود بخشی از Resolver ها برای مدتی پاسخ قبلی را نگه دارند.

چگونه می توان نیم سرور دامنه را تست کرد؟

بهتر است بررسی Name Server فقط با یک ابزار انجام نشود. بهتر است ابتدا رکورد NS در سطح دامنه بررسی گردد و سپس پاسخ Authoritative برای A/AAAA، MX و TXT مقایسه شود. بررسی توسط چند Resolver عمومی و یک درخواست مستقیم از Authoritative Server دید دقیق‌تری نسبت به وضعیت واقعی ارائه می‌نماید. در خطاهای پیچیده، مقایسه مسیر Root → TLD → Authoritative مشخص می‌کند که ایراد در Delegation است یا درون Zone رخ می دهد.

جمع‌بندی

Name Server نقطه اتصال دامنه به زیرساخت DNS است و تعیین می‌کند پاسخ‌های معتبر DNS از کجا دریافت شوند. اطلاع از تفاوت آن با Resolver، DNS Record و هاست، برای عیب‌یابی و مهاجرت ضروری است. پیش از تغییر نیم سرور دامنه باید Zone مقصد آماده شده و رکوردهای وب و ایمیل منتقل گردند سپس Delegation در رجیسترار تغییر داده شود. همچنین باید در نظر داشت که DNS Propagation به رفتار کش و TTL وابسته است.
